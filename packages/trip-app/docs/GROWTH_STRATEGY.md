# 100万人に届くための成長戦略（体験・価値の設計）

> 作成日: 2026-07-14
> ステータス: ドラフト（ディスカッション用）
> 対象: `packages/trip-app`（グループ旅行の計画〜当日〜振り返り管理アプリ）

---

## 前提：100万人を分解すると何が必要か

旅行アプリは「年に数回しか使わない」episodic（間欠的）なサービスである。
100万人に到達するには、広告費を積む前に次の3点が噛み合う必要がある。

1. **招待で勝手に増える（バイラル）** — 1トリップ = 2〜6人という構造を成長エンジンに変える
2. **一度使った人が離れない（リテンション）** — 旅行と旅行の「間」を埋める
3. **代替手段（LINE＋メモ＋Notion）より圧倒的にラク** — 「これがないと無理」の瞬間を作る

現状の機能は「グループで使える便利なメモ帳」止まりで、この3つがまだ弱い。
ここを埋めることが本質。

---

## 1. 成長ループ：招待そのものを「体験の入口」にする 🔴最重要

旅行は構造的に **1トリップ = 2〜6人**。招待リンクは既に存在するが、今は
「参加してもらう手段」でしかない。ここを**アプリが自己増殖するエンジン**に変える。

- **アカウント不要で即・閲覧参加**
  招待リンクを開いたら、ログイン前に旅程が見える（編集時のみログイン誘導）。
  「まずGoogleログイン」が最大の離脱ポイント。閲覧は0クリックにする。
- **LINE共有の最適化**
  OGP画像（カバー写真＋タイトル＋日程）をリッチに自動生成。LINEに貼った瞬間に
  「ちゃんとしたサービス感」が出る＝クリック率が変わる。
- **役割の押し付けをやめる**
  幹事が全部やる構造だと幹事しか定着しない。「あなたの持ち物ToDo」「あなたの担当
  （宿の予約）」を各メンバーに割り振り、**全員に"自分ごと"の理由**を作る。
- **旅行後の共有アルバム**
  終わった旅を1枚のWebページとしてシェアURL化。参加していない人（親・友人）が見て
  「私も次使いたい」と入ってくる = **新規獲得の第2ループ**。

> 招待は「機能」ではなく成長そのもの。K > 1（1人が平均1人以上を連れてくる）を
> 作れれば、広告なしで100万人が視野に入る。

## 2. リテンション：旅行と旅行の「間」を埋める

年数回の利用では絶対にスケールしない。既存の
**`scraps`（トリップに紐づかない単独メモ＋タグ）** が最強の伏線になる。

- **「行きたい」を貯める場所（旅のクリップ）**
  Instagram・TikTok・Web記事で見つけた店やスポットを、旅行の予定がなくても
  クリップ。タグで「京都」「カフェ」等に整理。→ **平常時にも開く理由**ができる。
- **クリップ → 旅程へワンタップ変換**
  貯めたスクラップを、新しいトリップのスケジュールにドラッグで流し込む。
  「計画が一瞬で埋まる」体験が"アハ体験"になる。
- **過去の旅程の再利用**
  「去年の沖縄」を複製して日付だけ変える。リピート旅行・帰省で効く。
- **旅の記録が資産になる**
  訪れた場所が地図に貯まる「旅の足あと」。これ自体がSNS共有欲を刺激し、
  成長ループ（1）に戻る。

## 3. コア体験：代替手段を捨てさせる「圧倒的なラクさ」

LINE＋メモ帳より少し便利、では乗り換えてもらえない。
**「これがないと無理」**の瞬間を作る。

- **予約メール/URLを貼るだけで自動で旅程化**
  航空券・ホテルの確認メールやURLを貼ると、日時・場所・予約番号を抽出して
  スケジュールに自動配置。手入力ゼロが理想。ここは LLM で差別化できる最有力ポイント。
- **地図が主役**
  現状 `placeUrl` はただのリンク。行程を地図上に並べ、移動時間・順序の無理を可視化。
  「その順番だと戻る動線」を教えてくれる。
- **リアルタイム同期**（現状MVP対象外）
  複数人が同時に計画する場面で、last-write-wins の上書き事故は致命的。
  Durable Objects で共同編集にすると"Google Docs of 旅行"になる。
- **当日モード**
  計画画面と当日で見たいものは違う。「今どこ」「次の予定まで◯分」
  「予約番号ワンタップ表示」に切り替わる当日UI。

## 4. スケールを支える基盤（100万人時点で効いてくる）

- **PWA / プッシュ通知**
  「明日の集合は9時」を前日に通知。再訪トリガー＝リテンションの生命線。
  ネイティブ化の前にPWAで十分戦える。
- **オフライン対応**
  旅行先＝電波が弱い。当日に開けないアプリは使われない。
- **インフラ上限**
  D1 の書き込み上限、R2 の画像リサイズ（Cloudflare Images）は
  `SPEC_refined.md` 10章の懸念通り。100万人規模ならデータ設計と有料枠移行が前提。

## 優先順位（推奨）

| 順位 | 施策 | 理由 |
|---|---|---|
| 1 | 招待リンクのログインレス閲覧 + リッチOGP | 成長ループの分子。ここが詰まると何をしても増えない |
| 2 | scrapクリップ → 旅程変換 | 「間」を埋めリテンション化。既存の `scraps` を活かせる |
| 3 | 予約URL/メールの自動旅程化(LLM) | 代替手段を捨てさせる決定打・最大の差別化 |
| 4 | 旅行後の共有アルバム | 第2の獲得ループ |
| 5 | プッシュ通知(PWA) | 再訪トリガー |

---

## まとめ

現状の「グループで使える旅のメモ帳」から、次の循環へ進化させる。

**① 貯める（平常時） → ② 一瞬で計画になる → ③ 全員で当日を過ごす → ④ 思い出が次の誰かを連れてくる**

この循環が回り始めたとき、旅行という間欠的な行動でも100万人が視野に入る。
