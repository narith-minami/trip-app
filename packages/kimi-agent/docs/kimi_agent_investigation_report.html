EXECUTIVE SUMMARY

GitHub Issueへのラベル付与をトリガーに、OSSコーディングエージェントOpenHandsとMoonshot AIのオープンモデルKimi K2.7 Codeを組み合わせ、Cloudflare上のサーバーレス基盤だけで自動実装〜PR作成を行うシステムを検証した。GitHub Actionsに依存しない、アイドル時課金がほぼゼロのイベント駆動アーキテクチャを目指した。

調査・実装を進める過程で、当初の設計前提そのものを覆す発見があった。OpenHands CLIは2025年11月のV1刷新で「サンドボックスコンテナを必須としない」設計に変わっており、それに気づかないまま進めていたDocker-in-Docker（DinD）構成は丸ごと不要だった。この発見によりアーキテクチャを大幅に簡素化し、実装量・複雑性の両方を削減できた。本レポートは、その調査の経緯と実機検証の結果を記録する。

OpenHands CLI 仕様調査で判明した誤り

4件
誤り1
存在しないCLIフラグ --max-iterations
当初、反復回数上限をコマンドラインで--max-iterations 80のように指定する設計だったが、実際にはこのフラグは存在しない。他のAIエージェントがOpenHandsの文書を生成する際にhallucinateしたフラグ(--model, --workspace, --sandbox等も同様)が出回っていたことが調査で判明した。
  • 正しい方法: config.tomlの[core] max_iterationsでのみ制御可能(デフォルト500)
  • 教訓: Web上の二次情報だけでなく、実際のopenhands --help相当の一次情報で検証する必要がある
SPEC CORRECTION
誤り2
環境変数によるLLM設定はデフォルトで無視される
LLM_MODEL, LLM_API_KEY, LLM_BASE_URL等の環境変数は、V1系CLIではデフォルトで無視される。自動化で使うには--override-with-envsフラグの明示、またはconfig.tomlファイルでの指定が必須。
SPEC CORRECTION
誤り3
レガシーPyPIパッケージ openhands-ai の誤用
pip install openhands-aiはV0(旧世代)のSDKであり非推奨。現行のCLIはuv tool install openhands --python 3.12でインストールする(PyPI名: openhands)。呼び出し方もpython -m openhands.core.mainではなくopenhands --headlessコマンドに変わっている。
SPEC CORRECTION
最重要
V1アーキテクチャは「サンドボックス任意」が原則
2025年11月のV0→V1移行で、OpenHandsのアーキテクチャは「Agent / Conversation / Workspace / Event」に刷新された。V0は全ツール呼び出しをDockerサンドボックス内で実行することを前提としていたが、V1は"Optional isolation"(隔離は任意)という設計原則を採用し、デフォルトではホスト上で直接実行される。
  • V0の前提: 全実行はDockerコンテナ内で行う(mandatory sandboxing)
  • V1の前提: ローカル実行がデフォルト、サンドボックスは追加の安全性が必要な場合のオプション

DinD廃止という設計転換

1件
転換
「V1はサンドボックス不要」の発見がもたらした波及効果
Cloudflare Containersが2026年2月にDocker-in-Docker(DinD)をサポートしたことを受け、当初は「Cloudflare Container内でdockerdを起動し、OpenHandsが内部でさらにサンドボックスコンテナを作る」という二重構造を設計していた。しかしOpenHands V1の仕様確認により、この構造自体が前提から誤っていたことが判明した。
  • 気づいたきっかけ: ローカルでのDinD検証が「重い」という相談を受け、代替案を調べる過程でOpenHands CLIの実際のアーキテクチャ文書に到達
  • 結論: Cloudflare Container自体がすでに1タスク1回限りの使い捨て隔離環境であるため、内部でさらにDinDを組む必要はない
  • 波及効果: ベースイメージがdocker:dind-rootlessからnode:22-slimに変わり、entrypoint.shのdockerd起動待ち処理が丸ごと不要になった

考察

01 / 一次情報の重要性
二次情報の劣化速度は想像以上に速い
OpenHands CLIのように活発に開発されているOSSは、V0→V1のような破壊的変更が数ヶ月単位で起こる。ブログ記事やチュートリアルの多くは旧仕様を前提にしており、実装直前に公式リポジトリ・issueで裏取りする工程を省略できない。
02 / 設計の先行検証
「重い」という違和感が誤りの発見につながった
当初「ローカルでのDinD検証が重い」という運用上の懸念から代替案を探索したところ、そもそもDinDが不要という設計上の誤りに行き着いた。運用面の違和感は、設計の妥当性を疑うきっかけとして機能する。
03 / 実装しながらの検証
手を動かすことで机上の設計ミスが顕在化する
実際にpackage.jsonのスクリプト名がpnpm予約コマンドと衝突する、wranglerがworkspace内で警告を出す、といった問題は、コードを書いて実行するまで気づけなかった。設計書だけでなく実装・実行を並走させる意義が確認できた。
